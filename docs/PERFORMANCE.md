# 鼠标特效性能检查（2026-10-19）

本次保留所有现有特效，没有减少粒子、连线、涟漪或拖尾数量，没有降低画布 DPR、模糊半径，也没有限制帧率。

## 检查结果

本机查询到 i5-1340P 与 Intel Iris Xe Graphics，显示模式为 2160 × 1440。隔离测试 Chrome 的 ANGLE 渲染器实际使用 Intel D3D11，Canvas、GPU 合成和光栅化均已启用。这只能证明测试浏览器的配置，不能代表用户日常 Chrome、Edge 或 VS Code 预览的配置。

主要发现：

- 鼠标视差每帧在 `.hero-content` 等父节点更新可继承的 `--px/--py`，导致子元素跟着重新计算样式。基线跟踪中样式重算占据显著的主线程时间。
- 光标和视差使用固定的“每帧追赶比例”。例如外环每帧追赶 16%，帧率降低时，同一动画在实际时间上变慢，放大了拖延感。
- 卡片倾斜在每次更新时读取 `getBoundingClientRect()`，又把光泽坐标变量设置在整张卡片上，增加样式检查和潜在的同步布局开销。

## 修改

- 保持原有视差方向、深度及位移精度，直接更新六个目标层的 `transform`，避免传播继承变量。
- 光标、外环和视差按实际帧间隔计算缓动，保留原先 60 Hz 的追随感；30 / 60 / 120 Hz 下相同时间内的追赶量保持一致。
- 卡片只在进入、滚动、尺寸变化或语言切换后更新几何缓存；光泽位置变量只写入光泽层，保留倾斜、悬浮、渐变和玻璃扫光。
- 为两个小光标层增加 `will-change: transform`，帮助浏览器复用合成层。
- 更新首页资源版本，避免浏览器继续使用旧脚本。

## 同机前后对比

条件：隔离 Chrome headless、1440 × 900 CSS 像素、DPR 1.5、相同鼠标路径、CPU 4 倍限速、所有特效开启。基线使用修改前提交中的 fx.js、ui.js 和 style.css。

| 场景 | 修改前帧间隔中位数 | 修改后帧间隔中位数 |
| --- | ---: | ---: |
| 夜色首页 | 50.1 ms | 33.3 ms |
| 夜色模块卡片 | 66.5 ms | 33.3 ms |
| 浅色首页 | 50.0 ms | 16.7 ms |
| 浅色模块卡片 | 50.0 ms | 16.8 ms |

这些是单次自动化压力测试的 rAF 帧间隔，不是对日常浏览帧率的保证，也不是鼠标硬件的输入到显示延迟。机器负载、窗口大小、刷新率、浏览器扩展、电源模式和图形驱动都会影响结果。夜色主题保留持续动画，相比静止后休眠的浅色背景仍有更多绘制工作。

## 验证和复现

```powershell
node tests/fx.cjs
node tests/language.cjs
node tests/fx-browser.cjs --baseline
node tests/fx-browser.cjs
```

`tests/fx.cjs` 检查 900 帧的全部粒子及连线、原 DPR、网格缓存、按住涟漪及拖尾、主题切换、休眠恢复，并验证不同帧率下缓动时长一致。浏览器性能脚本使用临时配置，输出显卡信息及 trace / summary 文件路径；不会修改用户浏览器设置。`--baseline` 始终读取 Git HEAD，因此提交这次优化后应使用历史提交另做基线。

在日常浏览器用 Ctrl + F5 强制刷新后比较。若仍卡顿，可在 `chrome://gpu` 或 `edge://gpu` 检查 Graphics Feature Status，并对比同一页面、主题、窗口大小和缩放比例。未自动改动系统图形设置。

参考：[MDN：动画应按时间而非帧数推进](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)、[Google：动画渲染与样式、布局和绘制开销](https://web.dev/articles/animations-guide)。
